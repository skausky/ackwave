# Code review 2026-11-21: detection, CSI capture, backend

Scope: main/csi_core.h, main/main.c (firmware: capture, poking, detector, reports),
tools/analyze.py, gui.py State, web.py (serial, pump, threads), record.py, the HA add-on run.sh.
`make test`: all C (824) and Python suites pass. Findings are ranked; each says how it was checked.

**Status:** every finding below was fixed on the satellites branch the same day (commits 38eea5f firmware, eb5c26e Pi reconnect / SIGTERM / lag queue, 810dbaf per-link quiet levels), with tests.

## 1. RSSI-step recalibration fires during real motion and ends it (HIGH, confirmed in logs)
`md_update()` (csi_core.h ~1680) recalibrates when any AP stream's fast/slow RSSI differs by > 4 dB.
`md_recalibrate()` sets `floor = 0`, so `md_eval()` forces `motion = false` (a STATE,still mid-motion),
gives no verdict for ~10 s (floor_min_n = 100 at 10 Hz), and then learns the new floor (floor0,
not capped) **with the person still there**.
Evidence: sessions/raw-2026-11-19_1336.log.gz has 7 `collect,rssi` recalibrations; **6 of 7 came while
the last STATE was `motion`**. So it is a person (body in the path / standing near the board), not the
board being moved, that trips it.
Fix ideas (pick one, keep analyze.py's MotionDetector in sync, the score_lines test checks they agree):
- don't run the RSSI step check while `d->motion` (or within N s of it); require the step to persist
  through a still period;
- require the step on every live AP ACK stream, not any one stream;
- raise rssi_step_db / lengthen rssi_tau_fast, and/or clamp floor0 against the previous floor
  after an rssi recal (like fast_rise_max does).
Add a regression test: a sustained motion segment plus an RSSI drop must not produce `why=rssi`.

## 2. web.py never reconnects to the serial port (HIGH for the Pi hub)
record.py reopens the port on SerialException; web.py doesn't: `reader()` / `reader_src()` push
`#ERR` then `None`, `pump()` returns, and main() then sleeps forever ("dashboard stays up until Ctrl+C").
In the HA add-on (run.sh `exec python3 web.py ...`) the process never exits, so HA won't restart it
either: one USB glitch, a replug, or a board restart that re-enumerates USB leaves the hub dead until
someone restarts the add-on. Note the dashboard itself sends commands that make the board call
esp_restart() (APS,..., USE,...).
Fix: wrap open_port in a retry loop like record.py's (close, wait 2 s, reopen, skip_backlog, log
"Board reconnected"), per port in multi mode; or at least exit non-zero when input ends on a real port
so the add-on/supervisor restarts it. Test with a fake port that raises then recovers.

## 3. Logs are not closed on SIGTERM: truncated gzip (MEDIUM, seen)
`zcat` reports "unexpected end of file" for sessions/raw-2026-11-20_1427.log.gz and
raw-2026-11-19_1143.log.gz. web.py only cleans up on KeyboardInterrupt; a Docker/HA stop sends SIGTERM,
so `log.close()` never runs and whatever gzip still buffered is lost (and tools reading the file must
cope with a cut stream).
Fix: `signal.signal(SIGTERM, lambda *_: sys.exit(0))` in web.py main (finally then runs), and/or
periodically `raw.flush()` with `zlib.Z_SYNC_FLUSH` (gzip's `flush()` does a sync flush) every ~30 s
so a hard kill loses at most that much.

## 4. Glitch lockout makes the ACK stream look stale and hands the verdict to the router's own frames (MEDIUM, by reading)
In `md_update()` a rejected glitch packet returns before `s->t_last` is updated. During a lasting shape
change (not a router scan), ACK packets are rejected for up to glitch_hold (5 s), but `md_live()` uses
`t_last` with stale_s = 2 s, so after 2 s the ACK stream counts as dead and `md_max_scores()` lets the
AP's own-frames stream decide, the very source the comment says caused most false starts.
`md_scanning()` covers this only while `scan_until` is set (scan case).
Fix: treat a stream that is still being *heard* (`t_heard`) but in glitch lockout like the scan case
(keep suppressing the own-frames stream), e.g. a `glitch_until` / check `now - t_heard <= stale` and
`n_glitch` rising. Mirror in analyze.py. Test: steady ACKs with a 4 s shape switch must not let the
own-frames stream score.

## 5. One global floor for every stream (MEDIUM, design)
The floor is the p10 of the *max* short score across deciding streams, and one threshold applies to
all. With 2+ AP links (multi-AP select is planned) the noisiest link sets the floor, so a quieter
link's motion needs to beat 2.8x someone else's noise; and when the deciding stream switches (ACK
stream drops out, own frames take over, finding 4) the scale changes under the same floor.
Improvement: per-stream floors (ring per stream, or the k-score relative to each stream's own floor,
which `rep_k20()` already reports per link) and decide on max(score_i / floor_i). LinkDetector in
web.py already does this on the PC side, so there is precedent.

## 6. Poke addresses can collide between boards with close MACs (LOW now, latent)
`poke_ta(me, node)` = our MAC with the local bit flipped and `node` added to the last byte
(0..12 incl. REPORT_NODE). Two boards whose MACs share the first 5 bytes and differ by <= 12 in the
last share addresses: board A's ACKs for node k look like board B's ACKs for node 0, and A's
report-ACK address can equal B's device-poke address (spurious `rep_acked`). ESP32 MACs from one
batch are often 4 apart. Checked: the current 4 boards do not collide (different upper bytes), but the
3 ESP32-C5 boards coming at Christmas, bought together, may.
Fix: derive the TA from a hash of the full MAC (e.g. first bytes of SHA-256(mac||node), unicast +
local bit), or warn at runtime when a heard PEER's poke range overlaps ours.

## 7. Same-boot report replay after a hub restart (LOW, security)
`pkeys_save()` stores each board's boot but zeroes `seq`, so after the hub restarts it accepts any
recorded report from the *current* boot of a board with a seq above 0. Comment claims recordings of
an *earlier* boot are refused (true); same-boot ones aren't until the board's seq passes them.
Fix: on first report after a hub restart, require seq > (saved high-water mark) by saving seq coarsely
(e.g. every 1000 reports, accept only seq > saved + 0), or just document the window.

## 8. Unbounded queue between serial readers and the pump (LOW, perf on the Pi)
`queue.Queue()` in web.py main is unbounded. CSI lines arrive at ~130-200/s per board and each is
parsed with numpy, plus per-link MotionDetector/Doppler/Breathing/activity when per_link is on. If the
Pi can't keep up, memory grows and the live view lags behind real time without any warning.
Fix: report `q.qsize()` on the Debug page / log a warning above some size; consider `maxsize` and
dropping CSI (not control) lines when behind.

## 9. Smaller firmware items
- `print_task` is created with `xTaskCreate` (unpinned) though the comment at main.c:229 says every task
  touching the shared volatiles is pinned to the Wi-Fi core. It only touches them via atomics/seen_mux
  today, so no bug, but pin it (or fix the comment) before someone relies on it.
- `csi_pkt_t.buf` is CSI_MAX_LEN (384) but only CSI_OUT_LEN (128) is ever copied: the 32-deep queue
  wastes ~8 KB; with buf[128] the queue could be ~3x deeper for the same RAM (fewer n_qfull).
- `n_reply` is huge on this router: last STATS of raw-2026-11-20_1427 shows 96k pokes, 654k reply
  CSI callbacks (~6.8 per poke: the router's deauth retries). Each costs a CSI callback in the Wi-Fi
  task. Harmless so far, but worth knowing; a different poke frame type may not provoke deauths.
- The report hop to the hub's channel (poke_task) retunes twice every 500 ms with no detector reset.
  Check whether the first CSI after returning is an outlier (glitch counter / score spike at 2 Hz).
- `md_floor_step` qsorts 1200 floats once a second: fine, but a quickselect would do.
- `USE_DEFAULT` is matched by prefix (`USE_DEFAULTX` also restarts the board). Trivial.
- Keys sit in plain NVS; anyone with USB access can read them. Consider NVS encryption later.

## Checked and fine
- first_word_invalid zeroing subcarrier 1: in 20k real CSI lines subcarrier 1 was never zero, so it
  doesn't reach the detector.
- Command line parser, b64 encode/decode, TLV parsing (`hello_open`) bound-checks every section.
- USB output never blocks and never cuts a line (byte ring buffer send is all-or-nothing).
- Wrap-safe timing helpers, ACK matching by dmac + window.
